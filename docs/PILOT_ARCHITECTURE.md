# Умный Закуп: от демо к пилоту

## 1. Что есть сейчас (demo-режим хакатона)

| | Demo (сейчас) | Pilot (следующий шаг) |
|---|---|---|
| Где работает | статический сайт на Vercel, `https://umny-zakup.vercel.app` | внутренний сервер или облако заказчика |
| Данные | заранее рассчитаны и лежат в публичном файле `data.js` (продажи, остатки, себестоимость SE) | выдаются через API только после входа |
| Доступ | любой, у кого есть ссылка; поисковая индексация отключена | вход по учётной записи, роли |
| Номера накладных, клиенты | не публикуются (поля клиента в выгрузке нет) | обезличенный ID клиента хранится только на сервере |
| Офлайн | браузер сохраняет копию сервиса | данные не кэшируются в браузере (`no-store`) |
| Согласование | отметка «согласовано на этом устройстве» в браузере | журнал согласований на сервере |
| Результат | Excel для проверки и последующего импорта | обмен с 1С по расписанию после проверки |

Demo-режим **не защищён** и не выдаётся за защищённый: он подходит для показа на обезличенных или согласованных с заказчиком данных.

## 2. Pilot-режим

**Доступ и роли**
- Вход через корпоративную учётную запись (SSO) или логин и пароль с двухфакторной проверкой.
- Роли: *менеджер по закупкам* (расчёт, правка количества, согласование своих заказов), *руководитель* (согласование, просмотр всех), *наблюдатель* (только просмотр, без цен).

**Данные**
- Расчёт выполняется на сервере (тот же `engine/`), браузер получает только нужные строки через API.
- CORS разрешён только для своего домена; ответы с данными — `Cache-Control: no-store`.
- Service worker кэширует только интерфейс (HTML, CSS, JS), но не данные и не ответы API.
- Заголовки безопасности: HSTS, CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`.
- Исходные выгрузки 1С хранятся на сервере, в интерфейс не отдаются.

**Журнал согласования заказа** (каждое действие — отдельная неизменяемая запись)
- пользователь и роль, дата и время;
- ID согласования и ID заказа поставщику;
- хэш версии исходных данных и дата выгрузки;
- сценарий и параметры расчёта (срок поставки, согласование, пересмотр, прирост);
- по каждой строке: рекомендованное и итоговое количество, кто и почему изменил;
- комментарий, статус (черновик → на согласовании → согласован → выгружен → отменён), история изменений и отмена.

**Интеграция с 1С**
- Формат обмена согласовывается с ИТ заказчика (выгрузка документа «Заказ поставщику» или Excel/CSV установленного формата).
- Перед импортом — проверка: коды 1С существуют, кратность соблюдена, количество > 0, сумма в пределах бюджета.
- Формулировка до проверки интеграции: «Excel подготовлен для проверки и последующего импорта», а не «готово для 1С».

## 3. Какие данные нужны от заказчика

| Данные | Что даст |
|---|---|
| Цены закупки IEK, цены продажи и маржа по всем SKU | полная стоимость заказа, бюджет по всему ассортименту, оценка риска выручки и маржи |
| Даты прихода товара в пути Systeme Electric | учёт этого товара в календаре остатка |
| Плановые и фактические даты поставок за 6–12 месяцев | надёжность поставщика, страховой запас с учётом опозданий |
| Обезличенный ID клиента в продажах | поиск крупных продаж одному клиенту (серия накладных) |
| Клиентские резервы и подтверждённые заказы | свободный остаток и отдельное планирование проектов |
| Товары-заменители и семейства | предложение аналога при дефиците |
| Стоимость хранения | оценка стоимости излишков |

Расчёт риска в деньгах появится только при наличии цены продажи и себестоимости и будет помечен как прогноз:
`риск выручки = неудовлетворённый спрос × цена продажи`, `риск валовой маржи = неудовлетворённый спрос × (цена продажи − себестоимость)`.
